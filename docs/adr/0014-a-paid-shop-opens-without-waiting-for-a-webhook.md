# A paid shop opens without waiting for a webhook

Everything that turns a completed Stripe Checkout into an open shop — the `merchant_billing` row, the plan reconciliation, and the flip of `merchants.status` to `active` — was carried by a single delivery of `checkout.session.completed`. The browser's side of that was a poll: land on `/merchant?checkout=success`, re-read the shop every two seconds, and render `Setting up your subscription…` until the status changed. When the event did not arrive — an endpoint subscribed to the wrong events, a deploy mid-delivery, retries exhausted against a 500 — nothing else ever looked, so the poll never ended. A merchant who had just been charged sat on that sentence with no error, no retry and no way off the page. The hourly billing sweep (ADR 0011's shape, `billingSweep.ts`) does not cover this: its worklist is rows whose stored *deadline* has passed while their stored status still reads running, which is the lapse direction. A shop stuck at `pending` has neither.

So activation stops being push-only, the same way suspension already did. `POST /api/billing/sync` (`billingSync.ts`) lets the signed-in merchant's own dashboard ask the backend to re-read their subscription from Stripe and make the database agree, and the post-Checkout screen calls it on a bounded schedule — four attempts over ~15s — instead of polling a status nothing may ever change. Stripe stays authoritative and the webhook stays the fast path; this only repairs what the fast path missed, and is idempotent because on a healthy day it runs over a shop the webhook already opened.

Activation here is deliberately **narrower than the webhook's**. `checkout.session.completed` opens any shop because the event itself is the evidence that a Checkout just completed. This route has no event, only a live subscription — and a moderation-suspended shop has one of those too, so "live subscription ⇒ open the shop" would hand every suspended merchant a self-service undo of their suspension. A shop is therefore opened only when its stored billing status says it was closed for billing reasons, or was never open at all.

The subscription is chosen from the customer's whole list rather than from the stored `stripe_subscription_id`, because on the path this exists for that id is the stale one: a shop reactivating after a lapse still names the canceled subscription that closed it, and asking Stripe about that id would read `canceled` and leave a paid shop shut.

Running out of attempts is a state the merchant is shown — payment received, confirmation still missing, retry, and an address to write to — not an ellipsis that never resolves.

The same reasoning applies in reverse to `customer.subscription.deleted`, which decided whether to close a shop by comparing the ended subscription against the id stored on `merchant_billing`. That id is written by the activation events, so losing them makes the comparison lie in the dangerous direction: the row still names the old trial, its cancellation matches, and a shop that has just paid for a replacement is suspended. It now asks Stripe whether the customer holds any other live subscription before closing anything, and reconciles to that one instead — which is also what makes replaying a backlog safe, since the order the events come back in no longer decides whether the shop ends up open.

This was found in production on 2026-08-07: the live-mode webhook endpoint was configured as `/api/v1/stripe/webhook`, a path that does not exist, so every billing event had been answered `404 Not Found` by Hono and nothing webhook-driven had run at all.
